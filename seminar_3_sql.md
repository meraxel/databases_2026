Q1 (Уникальные рейсы и сортировка)
Разница между DISTINCT и GROUP BY: Результат выполнения и физический план запроса (EXPLAIN) в PostgreSQL для этих запросов будут идентичными. Оптимизатор запросов PostgreSQL понимает, что DISTINCT без других агрегатных функций семантически эквивалентен GROUP BY. Для обоих запросов будет использован один и тот же механизм — обычно это HashAggregate (с последующей сортировкой) или узел Unique, если данные уже отсортированы по индексу.

Использование ORDER BY: По умолчанию оператор ORDER BY применяет сортировку по возрастанию, поэтому явно указывать ASC не требуется. При сортировке строк с разным регистром (например, 'PG0001' и 'pg0001') в стандартной локали (C или UTF-8) PostgreSQL опирается на ASCII/Unicode коды символов. Заглавные буквы имеют меньший код, поэтому 'PG0001' будет выведено раньше, чем 'pg0001'.

Q2 (Аэропорты и выручка за билеты)
Двойной счет при COUNT(*): Да, произойдет двойной счет. Функция COUNT(*) считает каждую строку результирующего набора данных. Если один пассажир купил два билета, соединение (JOIN) создаст две строки. Если требуется посчитать именно уникальных пассажиров, нужно использовать COUNT(DISTINCT passenger_id). SUM(amount) при этом корректно сложит стоимость обоих билетов.

Рейсы без билетов и JOIN: Чтобы рейс без билетов попал в выборку, необходимо использовать LEFT JOIN от таблицы flights к таблице ticket_flights. При использовании INNER JOIN такие рейсы будут отброшены, так как этот тип соединения оставляет только те строки, для которых есть совпадения в обеих таблицах. При LEFT JOIN поля билетов будут заполнены NULL, и для вывода нулевой выручки можно использовать функцию COALESCE(SUM(amount), 0).

Q3 (Отмененные рейсы и города)
Аэропорты без рейсов: Аэропорт, не фигурирующий в flights, должен попасть в результат, так как из него действительно не было отмененных рейсов (поскольку не было никаких). Оператор NOT EXISTS корректно вернет этот город: подзапрос не найдет ни одной строки с этим аэропортом, вернет false, что оператором NOT инвертируется в true.

Ловушка NOT IN с NULL: По правилам трехзначной логики (Three-Valued Logic) в SQL, сравнение с NULL возвращает UNKNOWN. Если подзапрос в NOT IN возвращает список, содержащий хотя бы один NULL, выражение город NOT IN (..., NULL, ...) вычисляется как UNKNOWN, и строка фильтруется — в итоге весь запрос может вернуть пустой результат. NOT EXISTS лишен этой проблемы, так как он проверяет только факт существования строк, возвращаемых подзапросом, а не сравнивает конкретные значения полей.

Q4 (Места на борту и дубликаты)
Устранение дубликатов: Для устранения дублей можно использовать как DISTINCT, так и GROUP BY. С точки зрения эффективности и плана выполнения в современных версиях PostgreSQL разницы нет — оптимизатор построит идентичные планы с использованием узла HashAggregate.

Аномалия данных при JOIN: Если пассажир отсутствует в ticket_flights (билет сдан), но присутствует в boardings (посадочный талон), то при использовании INNER JOIN между таблицами tickets и boardings этот пассажир не окажется в списке. INNER JOIN отсечет запись из boardings, так как не найдет соответствующей ей записи в билетах.

Q5 (DDL и блокировки на живой таблице)
Блокировка ALTER TABLE: Команда ALTER TABLE требует эксклюзивной блокировки уровня таблицы — AccessExclusiveLock. Поскольку долгий SELECT COUNT(*) уже удерживает блокировку AccessShareLock, команда DDL встанет в очередь и будет ждать завершения транзакции с SELECT. При этом все новые запросы (даже обычные SELECT) также встанут в очередь за ожидающим ALTER TABLE, что может привести к простою.

Добавление колонки с DEFAULT в PG 11+: Начиная с PostgreSQL 11, добавление столбца с постоянным значением DEFAULT (не волатильным выражением) выполняется мгновенно и не требует перезаписи всех строк в таблице (table rewrite). Значение по умолчанию записывается только в системный каталог (pg_attribute). При чтении старых строк база данных автоматически подставляет это значение «на лету». Если впоследствии изменить DEFAULT на true, новые операции INSERT будут использовать true, а старые строки, физически не имеющие значения, продолжат возвращать false, сохраненное в каталоге на момент их создания.

Блокировки при CREATE INDEX: Обычный CREATE INDEX накладывает блокировку ShareLock, которая предотвращает запись (UPDATE, INSERT, DELETE) в таблицу на все время построения индекса. Чтобы база данных продолжала работать без блокировок на запись, следует использовать синтаксис CREATE INDEX CONCURRENTLY idx_flights_status ON flights(status);. Компромисс заключается в том, что построение индекса CONCURRENTLY займет значительно больше времени и создаст большую нагрузку на CPU/I/O, так как требует нескольких проходов по таблице.

Q6 (Агрегация и NULL в вычислениях)
Поведение AVG с NULL: Агрегатная функция AVG автоматически игнорирует значения NULL. Строки отмененных рейсов не будут включены ни в сумму задержек, ни в общее количество рейсов (делитель). На итоговое среднее значение задержки состоявшихся рейсов это никак не повлияет.

Разница COUNT: Результаты SELECT COUNT(aircraft_code) и SELECT COUNT(*) будут различаться, если в колонке aircraft_code присутствуют значения NULL. COUNT(поле) считает только непустые (NOT NULL) значения в конкретном столбце, в то время как COUNT(*) считает все строки в таблице целиком. Если на колонке aircraft_code на уровне схемы задано ограничение NOT NULL, результаты обоих запросов будут абсолютно одинаковыми.
